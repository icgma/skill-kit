# Existing .docx: Reading and Editing

All commands below live in `{skill_path}/scripts/verify/` (the directory
containing this skill's SKILL.md, then `scripts/verify/`). `V` below is shorthand
for that directory; invoke everything as `python3 V/<script>.py`.

## 0. Workflow (memorize this; everything else is detail)

```bash
python3 V/prep.py file.docx -o work/
# → work/unpacked/      the ONLY working copy: every edit happens here
# → work/baseline.docx  read-only reference (acceptance baseline); never edit it
# → work/view.txt       baseline view (body text + effective formatting + comments + revisions)
...edit...(any mix of approaches, see below)
python3 V/opc.py pack work/unpacked out.docx                    # closing step 1: repack
python3 V/verify.py out.docx --baseline work/baseline.docx     # closing step 2: acceptance
```

- **Both legs work on the working copy and can be mixed freely:**
  - python-docx (high-level API, handy for text edits / table filling):
    `with opc.edit_docx("work/unpacked") as doc: ...` — on entry it repacks
    temporarily to feed python-docx, on exit it writes back. python-docx
    re-serializes XML byte layout when saving; harmless, because acceptance is
    semantic.
  - lxml + this skill's scripts (surgery on revisions / comments / tables /
    fields / bookmarks): edit the XML under `work/unpacked/` directly. When
    writing your own script, import the shared layer — never reinvent:
    `measure` (units) · `walker` (traversal) · `revreg` (revisions and ids) ·
    `effctx` (effective properties) · `coords` (positioning) ·
    `ooxml_order` (element ordering).
- Re-running prep is harmless (an identical rerun short-circuits); prep refuses
  to rerun over an edited workspace — `-f` rebuilds (and discards all edits).
- Write discipline: for batched lxml edits, never share one final `tree.write`
  across batches — an exception midway silently loses finished batches. Write
  after each batch.

## 1. The view and the two coordinate systems

**Reading view.txt**: block lines `[N #id …]` are the body (as if all revisions
were accepted); the ` └ ` lines right below carry that block's inline facts;
`@` cards carry global facts. Full notation: `python3 V/read.py --legend` — do
not guess.

- For format-audit / format-compliance tasks, read the view to EOF — spec
  clauses hide inside body text, and reading only slices has actually missed
  them in real runs; other tasks may slice as needed. After a full read, grep
  to locate: `grep -n 'size=' view.txt | sort | uniq -c` gives the whole
  document's format distribution in one line.

**Two coordinate systems, one sentence: copy `#id` to target edits; use line
numbers `[N]` to read raw XML.**

| | Line number `[N]` | Paragraph id `#A1B2C3D4` |
|---|---|---|
| What it is | Positional sequence number assigned at render time; does not exist in the file | The w14:paraId attribute written into the file; prep has backfilled and deduped them |
| Stability | Shifts wholesale when paragraphs are inserted/deleted | Born with the paragraph, dies with it, never drifts |
| Use | `read.py file --raw N` for one block's raw XML; lxml bridge `body[N]` | Targeting for ALL write operations (`at` / `after` in plans) |

Two exceptions: a table row `[7 @tbl]` is not a paragraph and has no id (tables
are hand-written lxml; for merge shapes see §5 rule 10); a collapsed empty-run
line `[5-15 empty×11]` represents a range. Paragraphs you create yourself with
lxml have no id — comment anchoring by text does not need one; if you truly need
id targeting, mint your own (8 hex chars, <0x80000000, unique document-wide).
Paragraphs created by tools (track's new_paragraph) get an id automatically and
echo it back.

Five traps:

- **Anchors**: copying verbatim from a content line into `--anchor`/`replace`
  always matches (`\t`, `\\`-style backslash escapes are literal characters; the
  tools decode them). `(tab)`/`(f1)`/`(img1)` bracket placeholders are **not
  text** — an anchor hitting them breaks there; `«…»` encloses **revision text
  pending deletion** — handle it via revisions.py.
- **Fields**: in `└ f1 instruction → "result" cached`, the "result" is Word's
  cache — editing it gets overwritten on refresh. Edit the instruction or the
  referenced content instead; `@range [a–b] field … cached` means the whole
  block is cache region (e.g. a TOC).
- **Auto-numbering**: literal-looking strings like "Chapter 1" are generated by
  `@num` rules and do not exist in body text — never paste them into body text.
- **Styles**: write `w:pStyle` with the id (`@style a* … "Normal"` has id `a`),
  not the quoted display name; `~name` is a theme reference; `⚠UNDEFINED` =
  body references a style that does not exist — add the definition or fix the
  reference.
- **`&name`** is a format-string alias; expansions are in the header `@fmt`
  lines. Aliases are per-document and not comparable across files.

**The view is a map, not the original**: for `@skip`, `unexpanded`, or anything
you cannot read, use `read.py file --raw N` to see the raw XML — do not act as
if it does not exist. python-docx and lxml operate on the same tree and are
interchangeable: `Paragraph(body[N], doc)`, `Table(body[N], doc)` wrap any block
as a high-level object; fetch an element by id with
`coords.by_id(root, "A1B2C3D4")`.

## 2. Comments: comment.py

Comments touch six files in sync plus body anchoring. Use the script; do not
hand-craft:

```bash
python3 V/comment.py work/unpacked "comment text" --anchor "original text to mark" --at "#A1B2C3D4" --author "Zhang San"
python3 V/comment.py work/unpacked "reply text" --reply-to c5
python3 V/comment.py work/unpacked --resolve c5                  # --unresolve to undo
python3 V/comment.py work/unpacked --ops plan.json --dry-run     # batch for ≥2 ops; don't spawn one process per op
```

A batch plan is a JSON array whose keys match the CLI flags:
`[{"text":"comment","anchor":"original","at":"#id"}, {"text":"agree","reply_to":"c3"}, {"resolve":"c7"}]`.

- `--anchor` must match uniquely within the `--at` paragraph (or across the
  whole document if `at` is omitted); on no-match/multi-match it errors out —
  lengthen the anchor text. Anchors that span runs are split automatically.
- Batch is all-or-nothing: any failed op rolls back everything with zero
  writes and reports the op#. A reply may point at a comment added earlier in
  the same plan (new comment id = current max + 1; an empty document starts at
  c0; when unsure, `--dry-run` first and read the echo).
- `.docx` input is also accepted (`-o` output); `--initials` sets the
  signature abbreviation. After landing, follow the closing ritual as
  usual — only the diff reveals a misplaced anchor.

## 3. Revisions (tracked changes)

**Write revisions with track.py** (ids allocated document-wide,
delText/delInstrText converted automatically, rPr cloned to preserve character
styling, zero writes on failure — in one real 84-edit task, hand-writing these
hit three separate pitfalls):

```bash
python3 V/track.py work/unpacked --ops plan.json --dry-run --author "Zhang San"
```
```json
[{"at": "#A1B2C3D4", "replace": "studied", "with": "systematically studied"},
 {"at": "#B2C3D4E5", "delete": "Furthermore, "},
 {"at": "#C3D4E5F6", "del_paragraph": true},
 {"after": "#C3D4E5F6", "new_paragraph": "Added explanation paragraph."}]
```

- Other ops: `append` (append at paragraph end), `del_field` (delete a field;
  both complex fields and fldSimple are recognized). Targeting is always
  `at`/`after` + #id, **order is free** (ids never drift); for large batches
  `--dry-run` first (runs the full code path without writing); the echo prints
  one summary line per op, `--verbose` adds full old/new text; failure means
  zero writes plus the reported op#.
- **Scope boundary**: track's text ops address only body paragraphs; paragraphs
  inside table cells, headers/footers, footnotes, and SDTs are not supported —
  handle those per the four rules below (targets inside field
  instructions/cache regions are refused outright). Targets spanning
  comment/bookmark markers are automatically wrapped by marker group; the
  markers stay in place.
- Annotation mode: `replace`+`with`+`color FF0000` rewrites text in place and
  colors it, **producing no revision** (the redline gate honestly treats it as
  an untracked edit — use only for annotation-style tasks). `del_paragraph` =
  all runs wrapped in w:del + the paragraph mark ¶del.
- Four rules for when you still must hand-write more complex shapes:
  1. Deleted text uses `<w:delText>`, not `<w:t>` — otherwise the deleted text
     still renders;
  2. `w:id` must be unique across the whole document (all stories: document /
     headers / footnotes; `44` and `044` are numerically the same); start from
     the document-wide max + 1; `rPrChange` cloned during run splitting also
     needs a fresh id. The full revision-element roster and id authority live in
     `V/revreg.py` — take them from it when hand-writing;
  3. `w:author` is required; always write `w:date` in full ISO form
     (`2026-07-29T00:00:00Z`; date-only fails XSD);
  4. Field instructions inside `w:del` must change from `<w:instrText>` to
     `<w:delInstrText>` (acceptance checks this; a real past pitfall).
- Acceptance for revision tasks: the closing ritual plus `--redline` — it
  undoes the revisions **added** relative to baseline and then compares body
  text. **The contract is text-level**: any text residue is an untracked direct
  edit; untracked formatting edits (e.g. directly bolding) are caught by the
  diff (+b shows up) — both must pass before you may sign "all changes
  tracked". Baselines that already carry revisions also work.
- Cascading deletions of numbered objects: SEQ/REF fields renumber themselves
  after revisions are accepted and refreshed; literal figure captions, in-text
  "Figure N" references, and subsequent section-heading numbers **must be
  hand-edited one by one** (fields move on their own, plain text does not — a
  real past miss).

**Dispose of revisions with revisions.py**:
`python3 V/revisions.py in.docx out.docx --accept|--reject [--id 5] [--author "Zhang San"]`.
It touches only revision elements; range markers collapse and are preserved.
After accepting a full-paragraph deletion, no empty bullet remains (if a render
shows an empty bullet, verify in the XML first — do not "fix" it as a defect).

## 4. Element order: ooxml_order.py

Children of `pPr`/`tcPr`/`sectPr`/`tblPr` follow strict xsd:sequence order;
disorder is a violation. The order table is generated from the bundled wml.xsd —
never hand-copy it:

```python
import sys; sys.path.insert(0, "{skill_path}/scripts/verify")
from ooxml_order import insert_ord, ensure_child
ppr = ensure_child(p_el, "pPr")   # create the child container at its schema position
insert_ord(ppr, jc_el)            # insert the element at its schema position
```

- Same name, different type: the paragraph mark's `w:pPr/w:rPr` is CT_ParaRPr
  (`ins`/`del` sort before all formatting keys), ordered differently from a
  plain `w:rPr`; insert_ord auto-detects from the parent path.
- A plain rPr is a choice (only `rPrChange` must come last); writing it in
  Word's customary order is fine.
- python-docx's own setters already handle order and units; this tool is not
  needed when editing through it.

## 5. General OOXML rules

| # | Topic | Rule |
|---|---|---|
| 1 | Dual indent/spacing channels | `firstLine` (twips) and `firstLineChars` (1/100 char) are two independent inheritance channels, Chars winning. Clearing an indent requires zeroing both attributes; same for `left/leftChars`, `hanging/hangingChars`, `before/beforeLines`; when `hanging` is present, `firstLine` is inert |
| 2 | Three-state booleans | `<w:b/>` = on; `<w:b w:val="0"/>` = explicitly off (blocks style inheritance); element absent = inherit. To switch off inherited bold, write `w:val="0"`; to return to inheritance, delete the element |
| 3 | Field caches | In the view, `(f1)` placeholders and the result part of `└ f1 instruction → "result" cached` are Word's cache; edits are overwritten on refresh (track.py refuses text targets inside field instructions/cache regions). Edit the instruction or the referenced source (bookmarks, numbering definitions). **Correct on delivery is the default, not the exception**: fields in a deliverable (review / print / submission / judge acceptance) must be complete and usable — taking a TOC as the example, the complete solution = outer TOC field + entry-level PAGEREF subfields + body bookmarks + hyperlinks + rewritten cache values from real computation + `<w:updateFields w:val="true"/>` as a backstop; **a TOC field shell plus updateFields alone is an unfinished solution** (LibreOffice / judges / print pipelines do not refresh — it amounts to not fixing, and your own render self-check fools you). Only collaborative scenarios (the recipient will press F9 themselves) may ship shell+updateFields, and the delivery note must say so. Rewriting caches is the LAST step after all edits; this machine has no Word layout engine, so a soffice render can serve as an approximate proxy (±page-level drift); page numbers are whatever Word shows on open |
| 4 | Units | Always read/write via `import measure` (V/measure.py): twips / half-points / eighth-points / EMU / Chars / pct, all covered with integer precision. Only one trap to remember: `spacing@line`'s meaning depends on lineRule (1/240 line when auto, twips when exact/atLeast) — the same number, two meanings |
| 5 | Dual image sizing | An inline image's size lives in both `wp:extent` and `a:xfrm/a:ext`; both must change together (the same-named `a:ext` under `a:extLst` is NOT the size); OLE object size lives in `v:shape`'s `style="width:…;height:…"` |
| 6 | xml:space | Leading/trailing whitespace in `w:t` requires `xml:space="preserve"`, otherwise it is dropped (validate.py warns about this) |
| 7 | Page-break stacking | `pageBreakBefore` stacked with preceding empty paragraphs or an existing `(pgbr)` manual break produces a full blank page; before adding a page-break property, confirm the existing break mechanism in the view — never combine the two |
| 8 | docGrid | A section's `w:docGrid type="lines"` snaps line height to the grid, so a smaller `spacing@line` has no effect; set `snapToGrid w:val="0"` on the paragraph or adjust the grid. "Line spacing changed but the render didn't" usually comes from this |
| 9 | Compatibility namespaces | When a new XML part uses extension namespaces (e.g. w14), the root element must declare the `xmlns` AND list it in `mc:Ignorable`, otherwise MCE conformance is violated (parts generated by comment.py already handle this) |
| 10 | Vertical table merge | Hand-written lxml (no tool — medium frequency + hand-flattening put the ROI underwater): group head `vMerge w:val="restart"`, continuation rows bare `<w:vMerge/>`, both placed into tcPr via insert_ord; continuation cells clear their content but **must keep one empty paragraph and its pPr** (Word refuses to open a cell with zero paragraphs); never cross a gridSpan boundary; when clearing content around paired markers (bookmark/commentRange), keep the pairing — no orphans; after editing, follow the closing ritual |
| 11 | Column balancing | A continuous section break (type=continuous) that changes the column count triggers **column balancing** at the section end (both Word and LibreOffice), and the balancer ignores `keepNext` — a figure and its caption can split across columns. When figure+caption sit right before a full-width section, either switch to in-column scaling or accept the balancing result (real past incident) |
| 12 | Fixed column widths | Column width ≈ nominal glyph width (full-width ≈ font size, half-width ≈ half font size) + cellMar×2, plus **≥10% render headroom** — LibreOffice's fallback metrics run wider when fonts are missing, and zero headroom guarantees wrapping (real past rework); fixed-width tables always use `tblLayout fixed` + `tblW dxa`; declared widths (effective tblW / ΣgridCol / per-column constraints + leading tblInd) must not exceed the container (text body / column / host cell). Overwide declarations cannot be judged statically (engines scale or overflow inconsistently): acceptance **only warns**; such warnings cannot be confirmed by text checks — to confirm you must look at the render; hard failures are reserved for provable facts (duplicate revision ids, range pairing, dangling rels, etc.) |
| 13 | paraId | New paragraphs **do not need a self-minted paraId** (Word backfills on open; prep has backfilled and deduped existing ones; paragraphs created by track get ids automatically); if a hand-made paragraph needs id targeting, mint one: 8 hex chars, <0x80000000, unique document-wide |
| 14 | Header/footer discipline | For layout tasks, headers/footers by default only get a page-number field — but when the task text or an attached spec explicitly states header/footer content requirements, replacing per spec is a formatting matter, not a content change (real case: a spec-mandated fixed header sentence was a judge's scoring item — do not translate discipline into inaction); without explicit requirements, adding text IS a content change; in LibreOffice, behindDoc background images may cover headers/footers |
| 15 | Format tasks touch zero text | In pure formatting tasks (layout / styles / widths / page numbers), not one character of body text may change — spaces, full/half width, and punctuation all count as text; verify's body char multiset must equal the baseline's; "fixing a typo / adding a space while I'm here" is also a content change. Changing text (renaming / renumbering / polishing) requires an explicit task requirement |

## 6. Acceptance (closing ritual)

```bash
python3 V/opc.py pack work/unpacked out.docx
python3 V/verify.py out.docx --baseline work/baseline.docx    # revision tasks add --redline
```

verify semantics in one sentence: **with a baseline, checks, mechanical
repairs, and generated-content pitfalls apply only to what the edit introduced
relative to baseline — the original's own quirks stay untouched; without a
baseline (a newly created artifact), the whole file is your product and
everything is checked and repaired.** On failure it reports violations only —
no diff (a diff of an illegal file is not worth reading); fix and rerun the
same command. On pass it prints the semantic diff directly.

- Read the diff both ways: any unplanned entry = collateral damage (guards
  against over-editing); every intended item must appear — absence = the edit
  did not take effect (guards against under-editing).
- `--no-repair` reports without fixing; to inspect changes midway without the
  gate: `python3 V/read.py work/baseline.docx --diff work/unpacked`.
- (Optional) when you need to eyeball effects text cannot judge — pagination,
  overflow, shading: `soffice --headless --convert-to pdf <artifact> --outdir <tmpdir>`,
  render pages at low resolution and tile them into one contact sheet
  (`pdftoppm -r 60 -png` then a PIL grid), read the whole document in one
  image; render high-res single pages only for suspicious pages.

## 7. Delivery confirmation when uncertain

Real user documents are often "hybrid systems": hand-typed numbering coexisting
with auto-numbering, a template's textual instructions inconsistent with its own
geometry, multiple style sets coexisting in one document. Such conflicts cannot
be enumerated and this file makes no rules for them; handle them uniformly:

- Finish the parts you are certain about first;
- For uncertain parts, do not decide for the user, and do not skip the whole
  group either — do what is safe first (e.g. for auto-numbering, change only
  the formatting attributes), and leave a "needs your confirmation" section in
  the delivery note: what confusion was found, what interpretation was applied,
  what was left untouched, and what you recommend.
